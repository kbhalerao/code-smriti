Smriti 2.0Design note18 August 2026

Fingerprints Over Vectors

You asked whether Smriti can find code like a given function — to kill intra-repo duplication and to port fixes between repos. It can, but not with the signal it currently uses. Here is what the corpus measurements say, and three ways to build it.

Q1 Can we take a function and find that kind of function elsewhere?

Yes — the mechanism already exists and already works. Seeded on one function, it found its two copy‑pasted siblings in the same repo. But the ranking below the top three is noise.

Q2 Is the embedding model resolving enough for code?

No, and not marginally. Rename a function’s variables and the model can no longer tell a perfect structural clone from unrelated code. Its entire signal for code is identifier strings.

Q3 So what should 2.0 actually be built on?

AST k‑gram fingerprints, with the document tree as the partition. Zero false positives on the same test the embedding failed, no threshold to tune, and no LLM in the loop.

01

The search you have today finds the answer, then buries it

Every symbol in Smriti already carries a 768‑dimension vector. Finding similar functions needs no new infrastructure — pull a symbol’s stored vector, search it back against the index.

Seeded on fetch_url in kbhalerao/ssurgo — an async fetch with retries and exponential backoff — that search returns exactly the right thing at the top:

The three real clones score 2.449, 2.443 and 2.435. The first function with no retry logic at all scores 2.355. A 4% gap between a true clone and a merely topical neighbour — there is no threshold that keeps one and drops the other, and top‑k becomes an arbitrary guess.

That gap is the whole problem, so the next question is what causes it.

02

Caveat, stated plainly Renaming to meaningless names is the worst case. Real clones keep meaningful names, so the embedding would score better in practice — but only because the names carry the meaning it is reading. That is the diagnosis, not a reprieve. This is also not a nomic defect: code‑trained embedders lean on identifiers too, so swapping models moves the numbers, not the architecture.
03

Your corpus is clone‑and‑own, which makes porting a join, not a search

Cross‑repo duplication is not the obstacle you called it. It is the calibration data — and for porting, it is the mechanism.

That third number is the one to build on. Same relative path is a high‑precision predictor of correspondence. For porting a fix you mostly do not need to find the counterpart — you already know where it is.

Repo‑level clustering finds 14 families over 35 repos; the archetypal diverged fork is topsoil2.0 ↔ labcore at Jaccard 0.78 with 1315 shared files. But keep the join at file granularity — src/lib/js/auth.js recurs across repos with no repo‑level kinship at all, and that is the larger surface.

Why inter-repo duplication is the thing that makes intra-repo dedup work

A block appearing three times in one repo and forty times across the corpus is framework boilerplate. A block appearing three times in one repo and nowhere else is a refactoring target. Same intra‑repo count, opposite verdict — and the only discriminator is corpus frequency. You cannot do good intra‑repo dedup without the cross‑repo index.

Hygiene warning Several repo pairs sit at Jaccard 1.00 — the same repo ingested under two orgs (jayp-eci_labcoredemo ↔ kbhalerao_labcoredemo, ecinfosolutions_kernel_backend ↔ kbhalerao_kernel_backend at 0.99). They are not port targets. They inflate every count and will generate useless suggestions. Collapse them before ranking anything.

The hard part is not detection — it is exclusion. My first run was swamped by vendored jQuery, Angular i18n locales and DataTables sitting under Scripts/ and static/. Filtering vendored, minified and generated code cut the unit count from 76,843 to 23,870: 69% of what looks like code in this corpus is not yours. Corpus rarity does not save you here — a vendored library present in only one repo scores as “rare”. This needs a real vendored‑code classifier, and it is the main engineering cost of the feature.

Note what did not happen: zero “drifted” results. Reality is bimodal — the file is either effectively identical or gone — which matches the 67.6% byte‑identical figure from section 03. None of this classification needs an LLM. It is a path join, a hash match, and patch semantics.

05

What is in the way

One prerequisite has to be fixed regardless of which design you pick. The symbol_index layer is not currently a trustworthy symbol table.

  1. Stale generations accumulate. document_id hashes the commit, so re‑ingesting a changed file mints new documents and never deletes the old ones. fema/LOMRs.py has 12 functions on disk and 26 symbol documents across 6 commit hashes. farmworthdb carries 47 distinct commit hashes. Any similarity query returns ghosts of the query itself in the top slots.
  2. The LLM chunker invents symbol names and they land in symbol_index beside real tree‑sitter symbols. One function appears as fetch_url, fema_api_response_validation and fema_response_validation across three runs. Names like “PC Listing to Realstack Data Transform” are labels, not identifiers.
  3. Summaries are misattributed. listings/tests/test_realistack_helper.py is a test file, yet it is indexed under symbols named RealstackAPI.get_clients / get_users / get_cities — the client methods under test, which do not exist in that file. get_cities points at lines 134–157 (actually test_get_users_with_params) and carries a summary describing get_users.

The fix is the same in every option below: re‑key identity on (repo, path, symbol_name) with content hash as a field rather than part of the key, so re‑ingest becomes an upsert; and split parser‑derived symbols from LLM semantic units into separate document types instead of mixing identifiers with labels in one namespace.

06

Three signals and a tree — the corrected model

A fingerprint is a set of hashes, not a vector. You do not take cosine of it; you take set overlap. So this is not one object with two relationships — it is three separate signals answering three different questions, plus a tree that supplies context rather than distance.

Signal 1 · primary

Fingerprint overlap

“Is this the same code?” Set of k‑gram hashes per symbol, compared by Jaccard. Needs no threshold tuning because the classes do not touch, and degrades gracefully — edit 20% of a function and it still shares roughly 65% of its k‑grams, far above the 0.14 random ceiling.

Signal 2 · demoted

Embedding cosine

“Is this about the same thing?” Keep it, but only for the one question fingerprints cannot answer: someone reimplemented this from scratch sharing no tokens. That is a real question — and the only place this model earns its keep.

Signal 3 · cheap filter

AST shape metrics

Loop depth, branch count, parameter arity, call fan‑out. Too coarse to lead — random pairs already average 0.85 — but a nearly free pre‑filter and rerank feature once candidates exist.

Not a distance

Tree position

The document tree is the partition that turns a score into a verdict. The same fingerprint match means refactor this inside one repo, port candidate across two, and framework boilerplate across forty. One number, three meanings — only the tree tells you which.

The record, and the two queries

fingerprint_unit // one per outermost function/class, first-party only unit_id = hash(repo_id, file_path, symbol_name) // STABLE across commits repo_id, file_path, symbol_name, lang, start_line, end_line content_hash // a field, never part of the key -> re-ingest is an upsert fp[] // k-gram hashes of the normalised token stream (ids -> ID, literals -> LIT) shape{} // loop_depth, branches, params, calls, nesting is_vendored // the classifier that does 69% of the work fingerprint_df // the corpus-frequency table that makes results rankable fp_hash -> n_repos, n_families Query A — intra-repo duplication seed rare fp (df ≤ 3) -> candidates in same repo -> Jaccard ≥ 0.7 -> union-find rank by (copies - 1) × median_lines × corpus_rarity Query B — port a fix commit hunks -> path join into sibling repos -> match hunk pre-image classify: already-fixed | applies-clean | drifted | absent

Both queries read the same store. Neither touches the summary pipeline that drives your existing search.

07

Three ways to build it

These differ in where the structural index lives and how much of V4 they disturb. They are genuinely different bets, not a good/better/best ladder.

AQuery‑time, no index
Smallest bet

Store nothing. Fingerprint on demand from the 296 clones already on disk, driven by a CLI and an MCP tool. The full corpus pass takes minutes, and the clones are already kept current by incremental ingestion.

Buys youWorking answers in days. No schema change, no migration, no new storage, nothing to keep in sync. Easy to delete if the feature does not earn its place.
Costs youNo corpus‑frequency table without a full pass, so ranking is slow or approximate. No incremental updates. Nothing the RAG pipeline or the KPI dashboard can query.
BSibling structural store
Recommended

A separate content‑addressed store holding the two records above, built by an offline pass and refreshed by the existing incremental hook. V4 keeps doing summaries and semantic search, untouched. The two systems join on (repo_id, file_path).

Buys youBoth queries at full speed, incrementally maintained, with the frequency table that makes ranking meaningful. Zero risk to search that already works. The symbol‑identity fix can land here first and migrate into V4 later.
Costs youTwo stores to keep coherent, and a second definition of “what is a symbol” until they converge. Needs the vendored‑code classifier before results are usable.
CUnified symbol spine
Largest bet

Fix symbol_index properly: stable identity, parser symbols split from LLM units, and fingerprint plus shape plus embedding all carried on one document. One record, one truth, every signal co‑located.

Buys youThe cleanest end state. Hybrid ranking becomes trivial, the identity rot in section 05 is fixed at the root, and there is no second store to reconcile.
Costs youA full re‑ingest of 94K symbols and an FTS schema change, with search degraded while it lands. It couples a feature that is unproven to a pipeline that currently works.

I would take B. Not because A is wrong — it is genuinely the fastest way to see whether the intra‑repo results are worth acting on — but because the corpus‑frequency table is what separates a refactoring target from boilerplate, and that table wants to be persistent. C is the right end state and the wrong starting move: it bets a working search pipeline on a feature nobody has used yet. B reaches C incrementally, and the identity work is the same work either way.

08

Where I would start

  1. The vendored‑code classifier. Unglamorous, and it does 69% of the work. Path heuristics plus minification detection plus known‑library fingerprints. Everything downstream is noise without it.
  2. Collapse the mirror repos. Jaccard‑1.00 pairs under two orgs are one repo. Cheap, and it stops both features producing nonsense.
  3. The fingerprint pass and frequency table — the prototype behind section 04 already does this; it needs productionising, not inventing.
  4. Ship intra‑repo duplication first. It is self‑contained, it proves the fingerprinting, and there are 887 clusters waiting.
  5. Then porting, which adds only the path map and the four‑state classifier on top of the same store.

Symbol identity (section 05) is a prerequisite for all of it and should land alongside step 3.

Method & caveats

All figures measured 18 August 2026 against the 296 clones in $REPOS_PATH and the live code_kosha bucket. Embedding figures use nomic‑embed‑text‑v1.5 with the search_document: prefix, matching the ingestion path. Fingerprints are 5‑grams (Python benchmark) and 6‑grams (corpus prototype) over a token stream with identifiers and literals collapsed to placeholders.

Two limits worth carrying forward. The near‑clone bucket in section 03 used difflib.quick_ratio, an upper bound, so treat 20% as optimistic — the 67.6% byte‑identical figure is exact and solid. And the clone benchmark alpha‑renames identifiers to meaningless names, which is the worst case for the embedding rather than the typical one.

Prototype sources: dedup.py (corpus fingerprinting), cluster.py (intra‑repo clustering with rarity weighting), port.py (cross‑repo patch classification), discrim.py and realcorpus.py (signal benchmark).
