Smriti 2.0 · Design note 02

The Judgment Layer

An inspector for the smriti corpus, and the argument that its real job is not browsing but making summary quality measurable for the first time.

2026-08-19 Internal · code-smriti Companion to “Fingerprints Over Vectors”

01What this is for

A three-column browser over the smriti corpus: repository navigation on the left, source in the centre, smriti's own metadata on the right. Internal only.

The stated goal is to see what indexing information is being captured at the symbol, file, module and project level. That is worth building. But it is worth being precise about which question it answers, because it is not the one that has found anything so far.

Every defect caught this month was found by aggregate measurement, not by looking at a file: 10,433 classes with no documents, 21,055 symbols sharing a single id, 34% of “symbols” turning out to be LLM-chunker regions. The class gap in particular hid because the file-level view looked fine — you would have opened a file, seen five method documents, and moved on. Per-file counts looked plausible throughout.

The job

A browser is the wrong instrument for finding what is broken. It is the only instrument for the question aggregates cannot reach: is this summary any good?

Presence is now measured exhaustively. Quality has never been measured at all. Nobody has read one of the 12,128 class summaries written yesterday.

So the tool's job is quality adjudication, not defect discovery. That distinction drives every decision below.

02Why this is buildable now

An annotation anchored to a smriti document_id was impossible a week ago. Ids hashed the commit, so every re-ingest minted a new document and orphaned whatever pointed at the old one. Location-based identity is what makes a durable annotation layer viable.

The same change has a second edge, and it is the one that shapes the schema in section 06. Documents are now upserted in place. Under the old scheme a judged document sat frozen forever, orphaned but intact; now the next ingest silently overwrites it. Durable anchors, mutable subject.

03Where it lives

Chief of Staff is the right shell — authentication, TLS, domain and the write-back target all already exist there. But CoS is a separate repository (three containers: cos-web on :3000, cos-api on :8001, cos-mcp on :8002), and that creates two problems if its page reads code_kosha directly.

First, smriti's schema knowledge would live in a repository that does not move when smriti's schema moves. Yesterday's semantic_unit split would have broken such a page silently — it would have gone on reading symbol_name and presenting chunker regions as parsed symbols. That is the same failure mode as a parser fix that never reaches the corpus, one level up. Second, the source pane reads from repos_path on disk, so the CoS container would need a bind mount of smriti's clones purely to render a page.

The seam

smriti exposes a read API in api-server — /api/inspect/* for tree, document chain, neighbours and file content. The CoS page is a presentation-only client of it.

api-server already runs on the host with repos_path, so no mount. Schema knowledge stays where it changes. CoS gains a page, not a dependency.

Worth noting: clients/web-ui in this repo is already a SvelteKit 2 / Svelte 5 app with server-side Couchbase access and auth wired up — but +page.svelte is two lines and nothing is deployed. It is a viable alternative shell, at the cost of standing up a vhost and a second login. CoS is the cheaper path.

Three panes. The red entry on the left is a file present on disk with no file_index document — an absence the filesystem tree alone cannot show, and the document tree alone cannot either.

Left — the document tree, overlaid on the filesystem

These are not the same tree, and the difference is the information. Render the filesystem and you get a comforting hierarchy where everything appears present. Render smriti's own hierarchy — repo_summary → module_summary → file_index → symbol_index/semantic_unit — and the holes appear as holes. Neither alone can show a file that exists on disk but was never indexed, which is the single most valuable thing this pane can display.

Centre — source from disk, and that is a feature

smriti stores no file content, only summaries and spans, so the centre pane reads repos_path directly. Every symbol's start_line/end_line therefore renders against current disk content. If the tint lands on the wrong function, staleness is visible in a glance rather than inferred from a query.

Stronger: symbol and file documents now carry content_hash. Comparing it against a live hash of the span turns that glance into a hard bit. The span tint costs nothing and is essential; syntax colouring needs a dependency and can wait until reading unhighlighted source genuinely grates.

Right — an ancestry stack, not a property sheet

The premise of the v4 hierarchy is that summaries roll up, and the defects still outstanding are rollup defects — module summaries that do not reflect their files, roughly 472 dangling file→module links. Showing symbol, file, module and repo summaries simultaneously is how a rollup lie becomes visible. A tabbed property sheet hides exactly the comparison worth making.

The fourth pane: neighbours

Click a symbol, see its top-k from the vector index with scores and source inline. This is cheap — the symbol's own 768-float vector is already stored, so kNN needs no model in the frontend — and it is the one thing a terminal cannot do, because judging similarity means reading two blocks of code side by side.

It is also the evaluation harness for the whole 2.0 similarity effort. The companion note established that embeddings separate renamed clones from random code by +0.034, where AST k-gram fingerprints manage +0.973. Right now that is a number in a table. A neighbours pane makes it something you feel, and when fingerprints exist the same pane shows both rankings against each other.

05Write-back

“Findings, updates, issues” are three things, and only one belongs in CoS.

ObjectLives inWhy
Judgment
this summary is wrong		 code_kosha
as annotation		 Per-symbol, high-volume, meaningful only beside the document. Put these in an inbox and there will be twelve thousand notes by Friday.
Issue
the chunker mislabels test files		 CoS Few, need state and follow-up, and CoS already does that. Carries links back to the documents that prompted it.

Promoting a judgment to an issue should be one click. They should not be one object.

The four verdicts

A verdict axis, not a taxonomy of failure modes — four slots cannot hold a taxonomy and it would be outgrown within a week. Failure modes go in the note.

VerdictMeansRoutes to
goodI would ship it. Enough to find this code and decide whether to open it.baseline
genericTrue, but carries no discriminating information. “This function processes data.” Nothing false.the prompt
inaccurateDescribes this code, says false things about it.the model
misattributedPoints at the wrong code — summary describes something defined elsewhere, or the span highlights the wrong lines.a pipeline bug

generic is the important one. It is the dominant failure mode of LLM summarisation and it is invisible to every automated check in the stack — schema-valid, non-empty, correctly attributed, and useless. Nothing else measures it.

misattributed is not hypothetical: listings/tests/test_realistack_helper.py, a test file, was indexed under RealstackAPI.get_users and get_cities — the names of the client methods it tests, none of them defined in that file.

“Bad” is simply not good, so aggregation never needs to enumerate the failure modes. Deliberately squeezed out: “this should not be a document at all” — a significance-threshold call rather than a summary judgment. It goes in the note.

06The annotation document

// append-only; current verdict is newest per (target_id, author)
{
  "type":        "annotation",
  "target_id":   "<smriti document_id>",
  "target_type": "symbol_index | semantic_unit | file_index | module_summary | repo_summary",

  "verdict":     "good | generic | inaccurate | misattributed",
  "note":        "free text",
  "author":      "...",
  "created_at":  "2026-08-19T09:14:22",

  // anchor — lets a dangling annotation be re-attached rather than lost
  "anchor": { "repo_id", "file_path", "symbol_name", "start_line", "end_line", "content_hash" },

  // snapshot — what was actually judged
  "judged": { "content", "summary_source", "enrichment_level",
              "pipeline_version", "schema_version" }
}

Append-only, because you judge, fix, and re-judge, and the delta is the measurement. Current verdict is newest per (target_id, author) — which is exactly what v4/doc_versions.newest_per_key already does. No embedding, and no annotation entry in code_vector_index: these are not search targets.

Why the snapshot block is load-bearing

Stable identity makes the anchor durable but makes the subject mutable — the next ingest overwrites the judged document in place. Without a snapshot of the summary text and its provenance, the eval set decays into unfalsifiable claims about text that no longer exists.

The trap most likely to be fallen into

An annotation must record summary_source, enrichment_level and pipeline_version at judgment time. A summary judged good under gemma4 is not evidence about qwen.

Skip this and the eval set silently mixes generations — precisely the rot that took two days to purge out of the corpus itself.

Where the anchor will fail

CaseBehaviour
Named symbol, re-ingestedId unchanged. Annotation holds.
Named symbol, moved down the fileId unchanged — this is why name-keying was kept. Annotation holds.
Symbol renamedNew id. Annotation dangles.
Anonymous or colliding symbol, movedSpan-keyed, so new id. Annotation dangles.

A dangling annotation is re-attachable rather than lost: the same content_hash found elsewhere in the file means the symbol moved. Anything not re-attachable is shown as stale, never silently dropped.

07Open decisions

indexes
The inspector's core queries — children of a file, children of a module, annotations by target — are precisely the ones with no index. Either adopt the per-repo fetch pattern or add real indexes; either works, but it must be a decision rather than a discovery.
highlighting
Span tint first, free. Syntax colouring costs a dependency; defer until reading unhighlighted source proves painful.
authorship
Single-author for now. The (target, author) key already admits a second judge, and inter-rater disagreement is the honest measure of whether the rubric is real.

Existing indexes on code_kosha

idx_user_repo       (user_id, repo_id, type)
adv_repo_id         (repo_id)
idx_repo_doc_stats  (repo_id, type, metadata.language)
                    WHERE type IN [file_index, symbol_index,
                                   module_summary, repo_summary]

Note that semantic_unit is absent from that condition — a type added yesterday whose covering index was never extended, so those queries fall back to adv_repo_id and filter. Working, slower than it should be, and being fixed independently of this design.

08Out of scope, on purpose

No findings queue. A second left-column mode listing stale hashes, dangling parents and the 230 files whose parse yields no significant symbols is a plausible feature — and every one of those cohorts has been found this month with ad-hoc N1QL that is far more flexible than any UI worth building. The browser should do what the terminal cannot.

No editing of summaries. A human-written replacement is a different object with different consequences: it must survive re-ingestion as an override rather than be silently overwritten. Worth doing, not worth conflating with judgment.
