Smriti v2

A new embedding model, chosen by measurement rather than by benchmark reputation, and the corpus repairs that had to happen first.

2026-08-1917 commits181,157 documents236 repositories

01The headline

The embedding model moves from nomic-embed-text-v1.5 to Qwen/Qwen3-Embedding-0.6B, stored Matryoshka-truncated to 768 dimensions.

It was chosen on retrieval — the workload the index actually serves — over 5,000 documents and 300 natural-language queries:

modelMRRrecall@1significance
nomic-embed-text0.7520.667—
Qwen3-Embedding-0.6B0.8860.8177.7σ
Qwen3-Embedding-4B0.8850.8070.9σ vs 0.6B
Qwen3-Embedding-8B0.8880.8200.1σ vs 0.6B

The smallest model captures the entire gain. Thirteen times the parameters buys nothing measurable, so v2 ships the 0.6B: it re-embeds the corpus in hours rather than half a day, and truncating to 768 costs nothing (0.884 against 0.886) while leaving both FTS indexes their existing shape. This is a model swap in the same slot, not a reindex.

The measurement that nearly went the other way

A first benchmark on clone detection said do not migrate — Qwen was better there too, but nowhere near enough to matter against AST fingerprints, which score 1.000 AUC where the 8B scores 0.877.

That benchmark was measuring the wrong thing. Retrieval is what the index does all day, and on retrieval the ranking inverted and the gap was large. Same models, same week, opposite conclusions — the axis you measure decides the answer.

Source per symbol also rises from 2,000 to 8,000 characters, since the model's window went from 2,048 tokens to 32,768. Stated honestly: 2,000 scored MRR 0.887 and 8,000 scored 0.890, which is under half a standard error and not an established gain. It was taken because it costs 56 minutes once, discards 4.3% of code characters instead of 25.9%, and choosing low and later finding it mattered would mean re-embedding everything again.

02Corpus repairs

None of the above was reachable until the documents being embedded were correct. Four defects, all of which had been silently wrong for months and none of which raised an error.

Documents were keyed by commit

Identity hashed the commit, so re-ingesting a file inserted a parallel generation rather than overwriting it. Cleanup ran on one narrow path only, so every full re-ingest stranded a complete generation; 1,835 files carried more than one. Identity now derives from location alone.

Unnamed symbols collapsed onto a single document

The parser writes the placeholder anonymous or arrow_function when it cannot name a symbol, and identity keyed on that name — so every unnamed symbol in a file hashed to the same id and overwrote its predecessors. 21,055 symbols corpus-wide shared an id. One file held a single document describing 51 distinct functions.

Classes measured three lines long

Until a parser fix in August, a class's extent ended at the first line of its body, putting every class under the significance threshold. Methods indexed normally, which is why per-file counts looked plausible and the loss stayed hidden. The parser fix reached almost nothing on its own — incremental ingestion is change-driven — so it needed a backfill.

14,950 documents had no language recorded

Ordinary Python, JavaScript and TypeScript files written before the schema carried the field. A document with no language cannot be routed to a grammar, filtered when sampling, or stratified into a training set.

03Also in v2

new Rust is parsed. A 52-file Rust repository held four documents — the .md and .toml files. .rs appeared in no extension list, so the source never reached the index at all. Now 746 symbols, 621 of them significant.

new A corpus inspector at /smriti: three panes over the document hierarchy, source tinted by each symbol's recorded span, summaries stacked from symbol up to repository, nearest neighbours by stored vector, and a four-verdict judgment layer that records whether a generated summary is any good — the first labelled data about summary quality, which has never been measured.

fix Listing repositories took twelve seconds and is now 0.077s. It aggregated 180,000 documents to produce counts already stored per repository. A partial index also went unused until the query constrained its leading key — same query, same index, 9.9s versus instant.

fix Commit embeddings were double-prefixed. Two layers each prepended search_document:, so every commit vector was embedded from search_document: search_document: ….

04Breaking, and what to know

Every vector had to be regenerated. 180,637 documents. A corpus holding two embedding spaces does not fail — it returns similarity scores that are numbers rather than measurements. Measured directly during the migration: the same document embedded by the old and new models scores a cosine of 0.02. Both vectors are 768-dimensional, both unit-norm, both perfectly valid to the index.

Why a dimension check cannot protect you

768 truncated from Qwen is the same shape nomic produced and a completely different space. The obvious guard passes while the space changes underneath it.

So the services agree at runtime instead: the re-embed writes an embedding_manifest into the corpus last, and the API checks it at startup. Its absence means a migration did not finish. Loud, not fatal — wrong results with a healthy service deserve a klaxon, not an outage.

Model, prefixing, dimensionality and batching now live in one module per service rather than as string literals at six call sites across two of them. Prefixing is model-specific and asymmetric: nomic took literal prefixes on both sides, Qwen takes an instruction on the query side only. Getting that wrong cost 0.11 AUC when measured.

Batching is bounded by an attention budget as well as a token budget, because attention is quadratic and a single token budget once requested a 182 GiB buffer outright. Sizing uses effective length rather than character count, since the model truncates at its sequence limit and a 200,000-character generated file therefore costs exactly what an 8,000-character one does. Together these took throughput from 4.5 to 12.9 documents per second.

05Not in v2

The similarity work this system was heading toward — structural fingerprints, clone detection, cross-repository change porting — is designed and benchmarked but not built.

The benchmarks are worth stating because they set the direction: AST k-gram fingerprints separate renamed clones from unrelated code at 1.000 AUC with zero false positives, where the best embedding manages 0.877 and recovers 38% of clones at a usable threshold. That is a modality limit, not a capacity one — text embeddings encode identifiers and topic, and renaming removes the identifiers. Thirteen times the parameters moves it by 0.075.

So embeddings do retrieval, and fingerprints will do structure. v2 makes the first of those substantially better and leaves the second to be built.
